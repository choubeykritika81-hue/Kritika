**Agile and Scrum**

Part 1: Agile Methodology Terms

1\. Agile

Definition: Agile is a software development approach where software is developed in small parts instead of building the entire application at once.

Detailed Explanation:

Agile focuses on continuous development, testing, customer feedback, and improvement. It allows teams to adapt to changing requirements and deliver software incrementally.

Why do we use Agile?

\- To deliver software faster.  
\- To improve customer satisfaction.  
\- To reduce development risks.  
\- To handle changing requirements.  
\- To improve team collaboration.

Real-Time Example:

Amazon wants to develop a shopping application. Instead of developing everything together, the team first develops login, then product search, then shopping cart, and finally payment functionality.

2\. Scrum

Definition:  Scrum is an Agile framework used to manage software development through short cycles called Sprints.

Detailed Explanation:

Scrum helps teams plan their work, develop features, review progress, and continuously improve. It defines specific accountabilities, events, and artifacts.

Why do we use Scrum?

\- To organize development work.  
\- To improve teamwork.  
\- To deliver useful features regularly.  
\- To identify problems early.  
\- To continuously improve productivity.

Real-Time Example:

A team plans to develop a login feature within a two-week Sprint.

3\. Sprint

Definition:A Sprint is a fixed time period of one month or less during which the Scrum Team works to achieve a specific Sprint Goal.

Detailed Explanation:

During a Sprint, the team plans, develops, tests, and reviews work. Every Sprint aims to produce a usable product increment.

Activities during a Sprint:  
\- Sprint Planning  
\- Development and testing  
\- Daily Scrum  
\- Sprint Review  
\- Sprint Retrospective

Real-Time Example:

A development team decides to create and test a shopping cart feature within two weeks.

4\. Iteration

Definition: An iteration is a repeated development cycle in which software is developed, tested, reviewed, and improved.

Detailed Explanation:

Iterative development allows teams to improve software gradually based on feedback. Each iteration can deliver new features or improvements.

Real-Time Example:  
\- Iteration 1: Develop login page.  
\- Iteration 2: Add forgot-password functionality.  
\- Iteration 3: Improve login security.

Difference Between Sprint and Iteration:

| Sprint  | Iteration  |
| ----- | ----- |
| Specific to Scrum | Used across different Agile approaches  |
| Fixed length of one month or less | Duration depends on methodology  |
| Has a Sprint Goal | May have an iteration objective  |

5\. User Story

Definition:A user story is a short description of a software feature written from the user's perspective.

Detailed Explanation:

User stories help developers understand what users need and why they need it. They support communication between customers, developers, and the Product Owner.

User Story Format:

As a \[user\], I want \[feature\], so that \[benefit\].

Real-Time Example:

As a customer, I want to reset my password so that I can recover access to my account.

Benefits:  
\- Helps understand customer requirements.  
\- Makes requirements easier to manage.  
\- Focuses development on user needs.  
\- Supports testing and feedback.

6\. Epic

Definition: An Epic is a large requirement or body of work that can be divided into multiple smaller user stories.

Detailed Explanation:

Epics help teams organize large features that may require several Sprints to complete.

Real-Time Example:

Epic: User Account Management

User stories:  
\- User registration  
\- User login  
\- Forgot password  
\- Update profile  
\- Delete account

7\. Story Point

Definition: Story points are relative estimation units used to estimate the effort, complexity, and uncertainty involved in completing a user story.

Detailed Explanation:

Story points help teams compare the difficulty of different tasks. They do not directly represent hours or days.

Many teams use a Fibonacci-like scale: 1, 2, 3, 5, 8, 13, 21\.

Real-Time Example:

| Task | Example Story Point |
| ----- | :---: |
| Change button color | 1 |
| Create login page | 3 |
| Payment integration | 8 |

8\. Acceptance Criteria

Definition:Acceptance criteria are conditions that must be satisfied for a user story to be accepted.

Detailed Explanation:

They define the expected behavior of a feature and help developers and testers verify requirements.

Real-Time Example: Login Feature

\- User must enter a valid username and password.  
\- Correct credentials should allow login.  
\- Incorrect credentials should display an error.  
\- Password should be hidden while typing.  
\- Empty required fields should show validation messages.

Part 2: Scrum Roles and Responsibilities

9\. Product Owner (PO)

Definition:The Product Owner is responsible for maximizing product value and managing the Product Backlog.

Responsibilities:  
\- Define and communicate the Product Goal.  
\- Prioritize product requirements.  
\- Manage the Product Backlog.  
\- Communicate with stakeholders.  
\- Help the team understand product priorities.  
Real-Time Example:

In an Amazon-like application, the Product Owner prioritizes payment integration because customers need to complete purchases.

10\. Scrum Master (SM)

Definition: The Scrum Master is responsible for establishing Scrum and helping the Scrum Team improve its effectiveness.

Responsibilities:  
\- Guide the team in Scrum practices.  
\- Help remove obstacles.  
\- Support effective Scrum events.  
\- Improve team collaboration.  
\- Encourage continuous improvement.

Real-Time Example:

Developers face a problem accessing a testing server. The Scrum Master helps the team coordinate with the responsible people to resolve the issue.

11\. Developers

Definition: Developers are Scrum Team members responsible for creating a usable product increment during each Sprint.

Responsibilities:  
\- Plan Sprint work.  
\- Develop application features.  
\- Test software.  
\- Fix defects.  
\- Maintain product quality.  
\- Adapt their work to achieve the Sprint Goal.

Real-Time Example:

Developers create the login page, implement authentication, test the functionality, and fix errors.

12\. Stakeholders

Definition:Stakeholders are people or groups who have an interest in, influence over, or are affected by a project or product.

Examples:  
\- Customers  
\- Business managers  
\- Investors  
\- End users  
\- Support teams

Responsibilities and Contributions:  
\- Provide business requirements.  
\- Give product feedback.  
\- Share customer expectations.  
\- Help identify improvements.

Real-Time Example:

Customers request UPI payment support. The Product Owner considers this feedback when prioritizing future features.

Note: The official Scrum Team consists of the Product Owner, Scrum Master, and Developers. Stakeholders contribute to the product but are not a separate Scrum Team accountability.

Part 3: Scrum Events and Artifacts

13\. Sprint Planning

Definition: Sprint Planning is a Scrum event where the Scrum Team plans the work for the upcoming Sprint.

Detailed Explanation:

The team discusses why the Sprint is valuable, what work can be completed, and how that work will be done.

Purpose:  
\- Define the Sprint Goal.  
\- Select Product Backlog items.  
\- Create a plan for completing the work.  
\- Establish a shared understanding of the Sprint.

Real-Time Example  
The team plans to complete login and registration functionality within two weeks.

14\. Daily Scrum

Definition: Daily Scrum is a 15-minute event for Developers to inspect progress toward the Sprint Goal and adapt their plan.

Detailed Explanation:

It helps Developers coordinate their activities and identify obstacles.

Common Discussion Questions:

What did I complete yesterday?

What will I work on today?

Are there any blockers?

These questions are optional, not mandatory Scrum rules.

Real-Time Example:

A developer reports that the login API is complete but testing is blocked because the test server is unavailable.

15\. Sprint Review

Definition: Sprint Review is a Scrum event where the Scrum Team and stakeholders inspect the Sprint outcome and discuss future improvements.

Detailed Explanation:

The team demonstrates completed functionality, gathers feedback, and discusses changes needed in the product.

Purpose:

Inspect completed work.

Gather stakeholder feedback.

Discuss product progress.

Adapt future priorities when needed.

Real-Time Example:

Developers demonstrate the completed login feature. Stakeholders suggest adding two-factor authentication.

16\. Sprint Retrospective

Definition: Sprint Retrospective is a Scrum event where the team evaluates how the Sprint went and identifies improvements.

Detailed Explanation:

The team discusses processes, communication, tools, teamwork, and quality.

Common Questions:

What went well?

What went wrong?

What can we improve?

Real-Time Example:

The team discovers that manual testing caused delays and decides to automate repetitive tests in the next Sprint.

Sprint Review vs Sprint Retrospective:

| Sprint Review | Sprint Retrospective |
| ----- | ----- |
| Focuses on product outcomes | Focuses on team effectiveness |
| Includes stakeholders | Conducted by the Scrum Team |
| Collects product feedback | Identifies process improvements |
| Helps adapt future product work | Helps improve future Sprints |
|  |  |

17\. Sprint Backlog

Definition: The Sprint Backlog is a plan maintained by Developers that contains the Sprint Goal, selected Product Backlog items, and the plan for delivering them.

Detailed Explanation:

It helps Developers organize and track the work needed to achieve the Sprint Goal.

Real-Time Example:

Sprint Goal: Develop secure customer login.

| Task | Status |
| ----- | ----- |
| Design login page | Completed |
| Develop authentication API | Completed |
| Connect frontend and backend | In Progress |
| Test login functionality | Pending |

18\. Sprint Goal

Definition: The Sprint Goal is the single objective that the Scrum Team aims to achieve during a Sprint.

Detailed Explanation:

It gives the team a common direction and helps Developers make decisions during the Sprint.

Real-Time Example:

Sprint Goal: Enable customers to securely log in to the shopping application.

Related work:

* Create login page.  
* Implement authentication.  
* Validate passwords.  
* Test login functionality.

Sprint Goal vs Sprint Backlog:

| Sprint Goal | Sprint Backlog  |
| ----- | ----- |
| Defines the objective | Defines the work and plan  |
| Explains why the Sprint matters | Explains what and how  |
| One shared objective | Contains multiple work items  |

19\. Definition of Done (DoD)

Definition: Definition of Done is a formal description of the quality standards that a product increment must satisfy to be considered complete.

Detailed Explanation:

It helps the Scrum Team maintain consistent quality and ensures that completed work meets agreed standards.

Real-Time Example: Login Feature  
A feature may be considered done when:

* Code implementation is completed.  
* Code review is completed.  
* Required tests pass.  
* Critical defects are resolved.  
* Documentation is updated.  
* Applicable security requirements are satisfied.


  
The actual Definition of Done depends on the organization's or Scrum Team's standards.

Acceptance Criteria vs Definition of Done:

| Acceptance Criteria | Definition of Done  |
| ----- | ----- |
| Specific to a user story | Applies to the product increment |
| Defines expected feature behavior | Defines shared quality standards |
| Example: Correct password allows login | Example: Required tests pass |
| Helps determine story acceptance | Determines whether work is complete |

Conclusion

Agile is an iterative software development approach that focuses on collaboration, continuous feedback, and incremental delivery.

Scrum is an Agile framework that organizes work into Sprints. The Scrum Team includes the Product Owner, Scrum Master, and Developers.

Scrum uses events such as Sprint Planning, Daily Scrum, Sprint Review, and Sprint Retrospective to support transparency, inspection, adaptation, and continuous improvement.

The Sprint Backlog organizes planned work, the Sprint Goal defines the objective, and the Definition of Done establishes quality standards for completed increments.
